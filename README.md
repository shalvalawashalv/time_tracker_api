# Time Tracker API

Backend-сервис для учета времени по активностям.

## MVP (в планах)

Пользователь может:

- зарегистрироваться
- залогиниться
- создать activity, например Algorithms / Backend / Reading
- запустить time session по activity
- остановить активную session
- добавить comment к завершенной session
- посмотреть список своих sessions
- отфильтровать sessions по activity и датам
- посмотреть суммарное время по activity

## Business rules

- Название activity должно быть непустым и уникальным.
- Нельзя запустить session для несуществующей activity.
- Нельзя запустить новую session, пока есть активная.
- Нельзя остановить уже завершенную session.
- Comment можно добавить только к завершенной session.
- В статистику попадают только завершенные sessions.
- Activity без завершенных sessions не попадает в статистику.

Пока пользователей нет: данные общие, проверка активной session глобальная.
Защита от одновременных стартов и остановок еще не реализована.

## Features:

- создание и просмотр активностей;
- старт и остановка временных сессий;
- добавление комментария к завершенной сессии;
- просмотр списка сессий и поиск по UUID;
- фильтрация сессий по активности и состоянию (`is_active`);
- подсчет суммарного времени и количества завершенных сессий по активности;
- сервисы переведены с хранения в словарях на PostgreSQL через SQLAlchemy.

Регистрация, авторизация, доступ только к своим данным и фильтрация по датам — в планах.

## Stack

- Python;
- FastAPI;
- Pydantic и Pydantic Settings;
- PostgreSQL;
- SQLAlchemy 2.x и psycopg 3;
- Alembic.

## База данных

- `activities` — активности: UUID и название до 200 символов;
- `sessions` — временные сессии: UUID, activity_id, начало, конец, длительность и comment;
- одна activity может иметь несколько sessions;
- UUID генерируется в Python, время начала session задается PostgreSQL;
- даты хранятся с часовым поясом;
- конец и длительность активной session равны `NULL`;
- ограничения БД проверяют непустое имя, порядок дат и неотрицательную длительность;
- конец и длительность session должны быть либо оба заполнены, либо оба `NULL`.

ORM-модели находятся в `app/db/models.py`, Pydantic-схемы — в `app/schemas/`.
Подключение и сессии БД настроены в `app/db/database.py`.
Маршруты получают сессию через `Depends(get_db)`, изменения сохраняются через
`commit()` в сервисах. При исключении выполняется `rollback()`, сессия закрывается
после обработки запроса. Статистика считается одним SQL-запросом через JOIN,
GROUP BY, SUM и COUNT.

## Запуск

Команды PowerShell из корня проекта. Если `.venv` еще нет:

```powershell
python -m venv .venv
```

Установка зависимостей:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

PostgreSQL должен быть запущен, база и роль созданы заранее.
Создайте `.env` по образцу `.env.example`, если его еще нет:

- `DATABASE_URL` — строка подключения с драйвером `postgresql+psycopg`;
- `DB_ECHO` — вывод SQL-запросов в лог, по умолчанию `false`.

`.env` с паролем не добавляется в Git.
Перед работой API с данными нужно применить миграцию.

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload
```

`GET /health` проверяет работу приложения, но не подключение к БД.

## Миграции

Для управления структурой БД используется Alembic.

- подключение через settings и `DATABASE_URL`;
- сравнение структуры БД с ORM-моделями;
- хранение миграций в `alembic/versions/`;
- создание таблиц `activities` и `sessions` миграцией `0001`;
- создание внешнего ключа, индекса, уникальности имени и проверок данных;
- таблицы при старте приложения автоматически не создаются.

Первая миграция `0001` применена к локальной PostgreSQL.
Создание и чтение данных через API проверены на PostgreSQL.
При запуске проекта с новой БД миграцию нужно применить отдельно.

Текущая версия БД:

```powershell
.\.venv\Scripts\python.exe -m alembic current
```

SQL первой миграции без применения:

```powershell
.\.venv\Scripts\python.exe -m alembic upgrade 0001 --sql
```

Применение первой миграции после проверки и согласования:

```powershell
.\.venv\Scripts\python.exe -m alembic upgrade 0001
```

Создание следующей миграции после изменения моделей:

БД должна быть на текущей версии миграций.

```powershell
.\.venv\Scripts\python.exe -m alembic revision --autogenerate -m "describe schema change"
```

Применение новых миграций после проверки созданных файлов:

```powershell
.\.venv\Scripts\python.exe -m alembic upgrade head
```

Проверка расхождений между БД и моделями:

```powershell
.\.venv\Scripts\python.exe -m alembic check
```

- Сгенерированные миграции нужно проверять вручную, особенно переименования и CHECK.
- Если таблицы уже есть, перед применением нужно сравнить их схему с миграцией.
- `stamp` без проверки соответствия схемы не используется.
- Откат первой миграции через `alembic downgrade -1` удалит обе таблицы с данными.
